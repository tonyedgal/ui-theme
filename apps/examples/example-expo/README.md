# UI-Theme native reference app

Expo SDK 57, React Native 0.86.3, and React 19.2.3. A native stack opens Appearance
and Preview. Expo UI pickers render as SwiftUI on iOS and Compose on Android.
The Transitions screen demonstrates nine optional Skia screen effects for both
appearance and palette changes. The package also provides separate 180 ms
Reanimated color styles for applications that need per-element transitions.
Native headers and Expo UI controls keep their platform behavior.
The provider restores appearance and palette preferences from Expo SQLite.

The TypeScript styling system is React Native `StyleSheet`/style objects with
`uitheme-rn` palettes and `themeTokens`. Expo UI provides the native controls.
Default, Supabase, Mono, Caffeine, Mocha, and Perpetuity use the Next example's
colors in light and dark modes. Forest and Clay remain available.

Run `pnpm --filter example-expo sync:colors` from the root after changing
`example-next/app/globals.css`. The shared generator also refreshes the two CSS
styling examples. Lightning CSS compiles OKLCH source values to native sRGB at
build time. All 32 tokens per mode are exported as `webColorTokens` from
`src/theme`; seven semantic colors supply the provider, controls, and navigation.
The native runtime imports generated TypeScript colors and needs no CSS engine.

See [VERIFICATION.md](./VERIFICATION.md) for the checks completed locally and
the remaining device checks. The browser preview uses a separate localStorage
adapter; native preferences use SQLite.

From the repository root:

```sh
pnpm --filter uitheme-rn build
pnpm --filter example-expo start
```

Use Expo Go matching SDK 57, or an app development build. For local native builds,
use `pnpm --filter example-expo exec expo run:ios` or `expo run:android` with the
matching platform tooling. Native directories are generated by Expo and are not
part of this example's source.

## Acceptance checks

- Select Light and Dark, then select Forest and Clay. Confirm the preview,
  navigation, status-bar content, and controls agree.
- Select System. Change the device appearance, including while the app is in
  the background. Confirm the active palette remains unchanged.
- Restart the app. Confirm both preferences restore before the launch screen
  disappears. Change choices rapidly and restart again.
- Use VoiceOver and TalkBack to reach each picker and make a choice. Confirm
  selected values and disabled state are exposed by the native controls.
- Use the largest accessibility text size, landscape, and a small screen.
  Confirm content scrolls, labels remain readable, and system insets are respected.
- Enable Reduce Motion and navigate to Preview and back. Confirm navigation uses
  a fade. The settings controls retain native feedback.
- Judge touch feedback and navigation in a release build on a slow device.

These manual checks must be recorded before claiming device-level verification.

## Transition checks and release performance

Open **Try screen transitions** from Appearance. Select an effect, then use
**Play appearance transition** or a palette button. The appearance button supplies
the origin for circular, heart, and star effects. Reduce Motion applies choices
immediately. Native system chrome can update outside the captured view tree.
See the package's [screen acceptance checks](../../../packages/ui-theme-rn/SCREEN-TRANSITION-CHECKS.md).

Run the cases in [TRANSITION-CHECKS.md](./TRANSITION-CHECKS.md) on each platform.
Enable Reduce Motion before launch and while the preview is open. Reverse a theme
change before its 180 ms transition ends. Verify the newest preference survives
a restart. Use the Accessibility Inspector and screen readers for focus checks.

For release performance, build with `expo run:ios --configuration Release --device`
or `expo run:android --variant release --device`. Use the slowest physical device
in the app's supported range. Record device model, OS, build mode, display refresh
rate, repeated reversals, frame hitches, and memory. Use Instruments on iOS and
Perfetto on Android. An Expo Go recording cannot establish release performance.

Do not publish from the reference app. The package release uses the workspace
Changesets workflow after packed-package checks and the device acceptance pass.

## Physical iPhone setup

The example uses bundle identifier `com.tonyedgal.uithemenativeexample`.
Connect and unlock the iPhone. Accept its Trust prompt. Local installation needs
Developer Mode on the phone, Xcode, CocoaPods, and an Apple development signing
identity. Set up signing in Xcode before running `pnpm --filter example-expo ios:release`.
The release script selects a device and includes the JavaScript bundle in the app.

`pnpm --filter example-expo ios:go` opens the Expo Go preview. This can help with
functional checks, but release performance must use the standalone release app.
Generated `ios/` and `android/` directories stay ignored. Change native settings
through `app.json` and regenerate with Expo prebuild.

For Xcode 27 and iOS 27, this example enables scene support through
`expo-build-properties` in `app.json`. Expo SDK 57 requires `expo@57.0.23` or
newer for this opt-in. After changing native configuration, regenerate with Expo
prebuild before building. The generated scene manifest and app delegate must both
be present; otherwise iOS stops the app at launch. See
[Expo's scene lifecycle guide](https://github.com/expo/fyi/blob/main/ios-scene-lifecycle.md).
